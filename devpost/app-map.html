TRACEBACK / Engineering cognition

Follow one diagnosis
from words to verification.

TRACEBACK is a single-case engineering knowledge-gap discovery proof of concept. A learner explains a transistor-amplifier gain drop; the app traces the reasoning evidence, offers a controlled bias experiment, then checks the same dependency on a related re-test.
What powers this proof of concept: authored deterministic evidence rules and a fixed circuit table. The app makes no runtime LLM/API calls and does not claim general natural-language understanding.

One real learner action through the app

Student explanation → evidence → visible result

  1. Write a diagnosisDiagnosticLab dispatches the student's text as SUBMIT_INITIAL.
  2. Gate and evaluatesessionReducer calls diagnoseReasoning; the sufficiency gate prevents empty or vague input from becoming a diagnosis.
  3. Keep evidence in memoryEach authored rule maps statements to a dependency status and explanation; the reducer retains the trace for this page session.
  4. Show and verifyThe map and trace expose the evidence. The experiment changes a preset; a re-test either repairs the target edge or reaches the bounded unresolved result.
Reference route · 3 stops

Read the implementation in this order

  1. Input and visible flow: web/src/components/DiagnosticLab.tsx — DiagnosticLab wires the reasoning field, experiment, re-test, map, and summary to session actions.
  2. Gate, rules, and state transitions: web/src/lib/diagnosis.ts — checkSufficiency, evaluateEdge, and diagnoseReasoning; then web/src/lib/session.ts — sessionReducer, SUBMIT_INITIAL, and SUBMIT_RETEST.
  3. Intervention and outcome: web/src/components/BiasExperiment.tsx and web/src/lib/circuitModel.ts define the controlled interaction/readings; web/src/components/SessionSummary.tsx and web/src/components/TraceComparison.tsx present the retained traces and final result.

These are reference pointers, not a claim that the learner has toured the files interactively.

Safe starting points

To change this, start here

  • Evidence language or sufficiency cues: web/src/lib/diagnosis.ts — review the authored patterns and their examples together.
  • Fixed bias readings: web/src/lib/circuitModel.ts — edit the preset table only alongside the approved case assumptions.
  • Challenge copy and view composition: web/src/components/DiagnosticLab.tsx; presentation rules live in web/src/app/globals.css.
  • Attempt limits or session transitions: web/src/lib/session.ts — keep the two-re-test boundary and trace preservation intact.
A practice to reuse

Turn “explain why” into observable evidence

The approved requirement asks TRACEBACK to show the student's statement, the dependency it supports or misses, and the reason for the status. The implementation separates the sufficiency gate from edge evaluation, then preserves evidence with the trace. The recorded browser verification checked empty/vague gates, a trace, both verification outcomes, and retained session history. On another project, turn a key requirement into a visible input → rule → cited evidence → outcome, then test one supported case and the edge cases that should not advance.

Run locally: from web/, run npm ci, then npm run dev; open http://localhost:3000. Run npm run lint and npm run build for the recorded checks.

Storage/services: browser-memory session only; no account, browser storage, backend, database, or runtime external service.
